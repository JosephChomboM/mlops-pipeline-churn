# MLOps Pipeline for Churn Prediction

[![CI](https://github.com/JosephChomboM/mlops-pipeline-churn/actions/workflows/ci.yml/badge.svg)](https://github.com/JosephChomboM/mlops-pipeline-churn/actions/workflows/ci.yml)
[![CD](https://github.com/JosephChomboM/mlops-pipeline-churn/actions/workflows/cd.yml/badge.svg)](https://github.com/JosephChomboM/mlops-pipeline-churn/actions/workflows/cd.yml)

A churn model built the way regulated industries build models and run the way MLOps teams run
them. Inputs are validated, probabilities are calibrated, decisions are priced, and drift and
delayed labels are monitored. Retraining ships a new version only if it beats the current
champion on a frozen holdout, and every champion comes with a model card generated from its own
artifacts.

**Stack:** Python · scikit-learn · MLflow · Pandera · SHAP · FastAPI · Docker · GitHub Actions
**Data:** [IBM Telco Customer Churn](https://github.com/IBM/telco-customer-churn-on-icp4d), 7,043 customers, 26.5% churn

```
                 ┌─────────────────────────── retraining signal ────────────────────────────┐
                 ▼                                                                          │
  Pandera ──► train + calibrate ──► quality gates ──► champion vs challenger ──► batch scoring ──► drift (PSI)
  validation   3 candidates         Gini, KS, ECE,    frozen holdout, $ value    + FastAPI         + delayed-label
  + DQ report  (MLflow tracking)    recall, gap       (MLflow registry)          parity-checked    Gini [CI]
                                         │
                                         └──► model card: SHAP, stress test, drivers, calibration, limitations
```

## The lifecycle

| Stage | What happens | Code |
|---|---|---|
| **Data validation** | Schema, ranges, allowed categories, unique IDs and null rate, checked before training *and* before every scoring batch. A bad batch is quarantined, never scored. | [`data/validation.py`](src/churn/data/validation.py) |
| **Data quality report** | Fill rate, cardinality, descriptives, duplicates, empty records and fill-rate stability across samples. | [`data/quality.py`](src/churn/data/quality.py) → [report](reports/data_quality.md) |
| **Reproducible training** | Frozen, hashed split. Every run logs params, metrics, dataset hashes (`mlflow.log_input`), the decision policy, calibration and driver tables, and the model with its signature. | [`models/train.py`](src/churn/models/train.py) |
| **Calibration** | The base model trains on 80% of train and a Platt calibrator on the other 20%, with no rows reused. Decisions multiply probabilities by dollars, so the probabilities have to be real. | [`models/train.py`](src/churn/models/train.py) |
| **Quality gates** | Test Gini ≥ 0.60, recall ≥ 0.60 on the business decision, train-test gap ≤ 10 Gini points, ECE ≤ 0.05. | [`models/evaluate.py`](src/churn/models/evaluate.py) |
| **Business layer** | Two rules compete on test: per-customer expected value (`p · p_accept · CLV > offer`) and the best global threshold. The rule that earns more ships with the model. | [`decision/policy.py`](src/churn/decision/policy.py) |
| **Promotion** | The challenger replaces the champion only if it earns more on a frozen holdout no model trained on, without losing more than 0.01 Gini. Promoting moves the `champion` alias. Rolling back moves it back. | [`models/promotion.py`](src/churn/models/promotion.py) |
| **Interpretability** | SHAP importance (one-hot columns summed back into their variable) and a ±1σ stress test. | [`models/interpret.py`](src/churn/models/interpret.py) |
| **Model card** | Purpose, population, target, samples, metrics per sample, calibration, performance by driver, SHAP, sensitivity, limitations and monitoring plan. | [`reporting/model_card.py`](src/churn/reporting/model_card.py) → [card](reports/model_card.md) |
| **Serving** | Batch scoring is the primary path and FastAPI covers lookups. Trained model, serialized artifact, batch and API return bit-identical scores. | [`serving/`](src/churn/serving/) |
| **Monitoring** | Feature and prediction drift. Realized Gini with a bootstrap CI and predicted vs. actual churn, computed only on cohorts whose 30-day label window has closed. | [`monitoring/`](src/churn/monitoring/) |
| **Retraining** | A drift or degradation signal retrains only if new matured, validated labels exist, and the challenger goes back through gates and promotion. | [`pipelines/orchestrator.py`](src/churn/pipelines/orchestrator.py) |

## Notebooks

The notebooks import everything from `src/churn`, so they analyze the same code that runs in production. Each one ends with the decisions it led to.

| Notebook | Key findings |
|---|---|
| [01 · EDA](notebooks/01_eda.ipynb) | Contract (IV 1.24) and tenure (0.82) dominate. Gender and phone service carry no signal (Gini < 0.02). Month-to-month on fiber churns at 55% vs 7% on a two-year contract. The frozen split is representative (max PSI 0.019). |
| [02 · Features](notebooks/02_feature_engineering.ipynb) | A plan change in either direction nearly doubles churn (U-shape). Derived features add only 0.003 Gini to a linear model, so they're kept for interpretability, not for lift. |
| [03 · Modeling](notebooks/03_modeling.ipynb) | A two-column business rule already reaches 0.62 Gini; the models reach 0.73. The three algorithms are statistically tied on ranking. Calibration cuts ECE from 0.13 to 0.03. The top 30% of the list holds 70% of churners. |
| [04 · Decision](notebooks/04_decision_and_interpretability.ipynb) | The expected-value rule earns $62.4k vs $45.3k at p ≥ 0.5 and stays profitable under every cost assumption tested. Half of the "missed" churners are left alone on purpose: they're not worth the offer. |
| [05 · Production](notebooks/05_production_review.ipynb) | Drift spreads to correlated features while demographics stay flat. **A paired bootstrap shows that none of the promotions was a real improvement** (challenger wins in 40-63% of resamples). |

## Six simulated months in production

Telco is a static snapshot, so time is simulated. 30% of customers are held out as a production
pool. Each month a cohort of 250 arrives, sampled with an increasing bias toward month-to-month,
fiber and electronic-check customers, the kind of population shift an aggressive acquisition
campaign would cause. **Labels are always Telco's real labels**, released to the pipeline only 30
days after the snapshot. In April an upstream system starts sending cents and renames a category.

`make simulate` reproduces this table ([`reports/simulation.md`](reports/simulation.md)):

| Month | Shift | Validation | Max feature PSI | Prediction PSI | Realized Gini [95% CI] | Predicted / actual churn | Signal | Action | Champion |
|---|---|---|---|---|---|---|---|---|---|
| Jan | 0.0 | ok | 0.042 | 0.042 | pending | – | – | – | v1 |
| Feb | 0.0 | ok | 0.033 | 0.059 | 0.516 [0.40–0.64] (Jan) | 26.0% / 26.8% | – | – | v1 |
| Mar | 1.0 | ok | **0.460** (contract) | **0.744** | 0.516 (Jan) | 26.0% / 26.8% | drift | retrain → **promoted v2** | v1 → v2 |
| Apr | 1.5 | **quarantined** | – | – | 0.523 [0.40–0.64] (Mar) | 42.1% / 40.8% | – | – | v2 |
| May | 2.0 | ok | **0.322** (internet) | **0.547** | 0.523 (Mar) | 42.1% / 40.8% | drift | retrain → **v3 rejected** | v2 |
| Jun | 2.0 | ok | 0.202 | **0.489** | 0.622 [0.52–0.71] (May) | 41.0% / 43.6% | drift | retrain → **promoted v4** | v2 → v4 |

- **Calibration holds under population shift.** The March cohort's churn rate jumped from ~26% to
  41%, and the model predicted 42.1%. Because the probabilities moved with the population, the
  expected-value rule keeps working.
- **A low point estimate didn't trigger retraining.** January's realized Gini (0.516) is under the
  0.60 gate, but its CI reaches 0.64. With 250 customers that's sampling noise. An earlier version
  of this pipeline retrained on the point estimate. The trigger now requires the whole CI below
  the gate.
- **Retraining waits for labels.** The March retrain could only use January, because February's
  labels weren't mature yet (28-day month + 30-day window).
- **The corrupted April batch was never scored.** Pandera caught 250 out-of-range charges and 192
  unknown `internet_service` values, and the cohort never entered a training set.
- **v3 passed every gate and was still rejected.** It earned less than v2 on the holdout.

### Promotion decisions (frozen holdout, 1,409 customers)

| Challenger | Model | Gini | KS | ECE | Net value | Result |
|---|---|---|---|---|---|---|
| v1 | gradient boosting | 0.667 | 0.523 | 0.022 | $61,655 | promoted (first model) |
| v2 | logistic regression | 0.673 | 0.514 | 0.029 | $61,926 | promoted |
| v3 | gradient boosting | 0.669 | 0.517 | 0.024 | $61,719 | **rejected** (less value than v2) |
| v4 | gradient boosting | 0.673 | 0.515 | 0.027 | $62,363 | promoted |

### Calibration and the decision rule

| Model (initial training, test) | ECE raw | ECE calibrated |
|---|---|---|
| Logistic regression (`class_weight="balanced"`) | 0.133 | **0.035** |
| Random forest (`class_weight="balanced"`) | 0.141 | **0.038** |
| Gradient boosting | 0.018 | 0.021 |

| Decision rule (initial champion, test) | Net value |
|---|---|
| Expected value per customer (`p · 35% · CLV > $60`) | **$36,004** |
| Best global threshold (0.16) | $34,933 |
| Default threshold 0.5 | $24,165 |

### What the model card found

- **Weak discrimination within long contracts.** Gini is 0.35 for one-year and 0.40 for two-year
  contracts, against 0.67 overall. Most of the signal *is* the contract type.
- **New customers are under-predicted.** For customers in their first six months the model predicts
  46.5% churn and the actual rate is 52.4%. Global calibration doesn't imply per-segment
  calibration.
- **Test is optimistic and the holdout is honest.** v1 scored 0.731 Gini on test (where the
  model and rule are chosen) against 0.667 on the holdout. That's why promotion never looks at
  test.
- **Linked features can't be stressed alone.** `total_charges ≈ tenure × monthly_charges`
  (correlation 0.9996), so shifting it alone creates customers that can't exist.

## Getting started

```bash
make setup      # venv + `pip install -e ".[dev]"`
make simulate   # init + six months (~40 s), writes reports/
make test       # 35 tests
make lint
make serve      # API on :8000, docs on /docs
make predict    # sample request
make mlflow     # MLflow UI on :5000
make notebooks  # re-execute the notebooks against the latest run
```

```bash
docker compose up --build api mlflow          # API + MLflow UI

```

## API

| Method | Path | Returns |
|---|---|---|
| `GET` | `/health` | Liveness/readiness |
| `GET` | `/model` | Version, run ID, retraining trigger, cohorts trained on, decision policy |
| `POST` | `/predict` | `churn_probability`, `contact`, `expected_value`, `risk_band`, `decision_rule`, `model_version` |
| `POST` | `/predict/batch` | Up to 1,000 customers. Anything larger belongs to the batch job |

Invalid payloads get a 422 before reaching the model. Every prediction is appended to
`logs/api_predictions.jsonl` with its request ID and model version.

## Design decisions

- **Batch first, API second.** Retention teams work from monthly lists, so auditability matters
  more than latency. Every batch row records the model version that produced it.
- **Calibrate on a separate split.** Calibrating on the rows the model trained on reproduces its
  overconfidence. `FrozenEstimator` keeps the base model fixed while Platt learns on unseen data.
- **Promote on value, guard on Gini.** A ranking metric doesn't say which model makes better
  decisions, and value alone could reward a degenerate model.
- **Frozen holdout separate from test.** Test picks the candidate and the rule. The holdout is
  touched only for promotion, and its hash is logged on every decision.
- **Gini and KS.** They're the standard discrimination metrics in banking model governance, so the
  gates are expressed in Gini.
- **Exact parity.** Allowing a tolerance between scoring paths would hide training/serving skew.
- **Two images.** The API image doesn't ship MLflow, SHAP or matplotlib.
- **PSI implemented directly** instead of pulling in Evidently: it's 20 lines and easy to test.
- **SQLite tracking store with registry aliases.** Stages are deprecated. In production this would
  be Postgres + S3.

## Known limitations

- **Promotion is decided on a point estimate.** v2 and v4 won by 0.4–0.7% of holdout value. The
  paired bootstrap in notebook 05 shows the challengers win in only 40–63% of resamples, so these
  promotions were noise. Next step: promote only if the challenger wins in ≥ 95% of resamples. Under
  that rule v1 would still be the champion.
- **Tuning.** Gradient boosting runs at depth 3; the grid search in notebook 03 prefers depth 2 (CV
  Gini 0.694 vs 0.682, within one standard deviation).
- **Segment-level calibration.** New customers remain under-predicted after global Platt scaling.
- **Simulated time.** Cohorts are disjoint customers, the drift is a covariate shift rather than
  concept drift, and there is no real out-of-time sample.
- **Simplified economics.** CLV is 12 months of charges and offer acceptance is a fixed 35%. Both
  should come from a retention experiment with a control group.
- **Fixed holdout.** It reflects the original population and should be refreshed (versioned) after
  a lasting shift.
- **Orchestration.** `pipelines/orchestrator.py` would become Prefect or Airflow tasks with
  retries and alerting, and `retrain.yml` would run against persistent storage.
